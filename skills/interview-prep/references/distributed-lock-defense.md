# 分布式锁选型防御模式

面试中常被追问"为什么用 Redis 不用 etcd？""etcd/Redis 挂了怎么办？"

## 推荐模式：分级选型（按锁生命周期选工具）

这是经过架构师 + 面试官双视角审查后的最终方案：

| 锁场景 | 工具 | 生命周期 | 选型理由 |
|--------|------|:--:|------|
| 请求级短锁（额度扣减） | **Redis SET NX** | 毫秒级 | 微秒级延迟，适合高频短锁 |
| 任务级长锁（定时任务互斥） | **etcd concurrency.Mutex** | 分钟级 | lease 自动续约零代码，CP 保证不双跑 |
| 兜底防线 | **MySQL SELECT FOR UPDATE** | — | 无论外层锁是否失效，保证不超额 |

## 面试叙事

```
面试官: "为什么有的用 Redis 有的用 etcd？怎么选型的？"

回答:
1. 定原则: "按锁的生命周期分级选型，不统一走单一工具。"
2. 短锁: "额度扣减是请求级——Redis SET NX 微秒级延迟，etcd Raft 共识 1-5ms。"
3. 长锁: "定时任务互斥是任务级——etcd lease 自动续约零代码，Redis 要达到同等可靠性需要自己写 watchdog + Redlock + Lua 释放。"
4. 兜底: "两层防线——外层锁串行化并发，MySQL 行锁兜底。各自容错链独立。"
```

## 降级路径（容错链独立）

```
Redis 锁失效（主从切换丢锁）
  → MySQL SELECT FOR UPDATE 兜底
  → 不会超额

etcd 锁失效（集群全挂）
  → 定时任务本轮跳过，下轮补偿（幂等）
  → 额度扣减不受影响（走 Redis 锁）
```

## 常见错误说法

- ❌ "etcd 锁负责性能层" — etcd Raft 延迟（1-5ms）高于 MySQL InnoDB 行锁（微秒级）
- ❌ "所有锁统一走一个工具" — 架构审查标为致命问题（故障域耦合 + 延迟不匹配）
- ❌ "Redis 短锁 + etcd 长锁分工" 解释为工具能力差异 — 两者都能做长短锁，差异在工程复杂度
- ✅ "短锁场景 Redis 更简洁（SET NX 一行），长锁场景 etcd 更可靠（lease 自动续约）"

## 追问应答

| 追问 | 应答 |
|------|------|
| "为什么不全用 Redis？" | 长锁要自己写 watchdog，工程复杂度高 |
| "为什么不全用 etcd？" | 短锁 Raft 延迟高 + 故障域耦合（etcd 还做服务发现） |
| "Redis 主从切换丢锁？" | MySQL 行锁兜底 |
| "etcd 集群挂了？" | cron 跳过补偿，额度扣减不受影响 |
| "谁决定用哪个锁？" | 看锁的持有时间：毫秒级→Redis，分钟级→etcd |

## Redlock 防御模式（清算定时任务互斥）

部分项目使用 **Redis Redlock**（而非 etcd concurrency.Mutex）做任务级长锁。面试追问集中在 Redlock 的时钟跳跃风险和 fencing token 缺失：

### Redlock 安全性争议的应答

> Martin Kleppmann 论文指出 Redlock 在时钟跳跃（clock drift）下有安全性问题——锁可能同时被两个客户端持有。

**实战应答框架：**

1. **承认风险但定位场景**："Redlock 的时钟跳跃风险在理论上成立，但在实际运维中——Redis 节点同机房部署，时钟偏差毫秒级。清算调度是 T+1 批处理，不是秒级实时对账，锁过期窗口放大到秒级也足够安全。"

2. **两层保护，不单点依赖 Redlock**："Redlock 做性能层准入（挡住 99.9% 的并发），MySQL 唯一约束做终局保护（挡住锁失效的极端情况）。同一批次/兑付 ID 不可能写两次。"

### Fencing Token 概念

面试官追问"为什么不加 fencing token"时，用准确概念应答：

> 锁服务给每个持锁者一个全局递增的版本号（token）。写数据库时携带 token，数据库检查 token 是否为当前最大值——不是就拒绝写入。

**为什么 etcd 和 Redlock 都没有 fencing token：**
- etcd 锁基于 lease + watch，不返回版本号
- Redlock 返回的是随机 UUID，不是单调递增版本号
- 两者都只做**准入控制**，不做**版本控制**

**替代方案（当前项目实际做法）：**
> "外层锁做快速准入，MySQL 唯一索引做终局保护——把版本判断从锁服务搬到数据库层。锁失效时，数据库兜底保证不重复清算。"

| 追问 | 应答 |
|------|------|
| "Redlock 为什么不安全？" | 理论上有时钟跳跃风险；实践中同机房部署，加上 T+1 批处理场景和 MySQL 兜底，不构成实际威胁 |
| "为什么不用 etcd 锁？" | etcd 锁也没有 fencing token，同样需要数据库兜底；Redlock 在清算场景下更简单直接 |
| "MySQL 兜底怎么实现？" | 清算批次写入时有唯一约束（批次号），同一个批次不可能重复提交 |

### Redlock 与 etcd 混用时注意

不同锁工具对应不同锁场景时，不要编造"Redlock 适合 XX 场景、etcd 适合 YY 场景"这种能力差异论。两者都能做长短锁。正确的说法是：

> "在我这个项目里 Redlock 负责清算互斥，因为 Redis 已经在集群里了，引入 etcd 只做锁是过度工程。至于 Redlock 的安全性问题——用 MySQL 行锁兜底解决，不单点依赖。"

## 银行结算日历（清算调度的面试追问）

### 获取途径

| 方式 | 具体做法 |
|------|---------|
| 银行接口查询 | 建行一般有"结算日历查询接口"，返回当年每天是否为结算日 |
| 银行静态文件 | 每年初银行发一份结算日历 CSV/Excel |
| 系统维护 | 维护 `settlement_calendar` 表，每年初根据银行日历初始化 |

### 关键经验

**不要用国家法定节假日推断银行结算日**——银行内部调休日和国家节假日不完全一致。T+1 可能变成 T+3。

### 面试应答

> "银行结算日历由资金方提供，系统里维护结算日表，清算调度根据日历决定提交和拉取时间。这是对接银行系统的基本功——不去猜银行的日历。"

## 模式演进历史（本 session）

最初使用"单工具统一锁架构"（所有锁走 etcd），架构审查发现两个致命问题：
1. etcd Raft 延迟不适合高频短锁
2. etcd 同时做服务发现+锁，故障域耦合

改为分级选型后，面试叙事从"栈统一"升级为"按生命周期选工具"，可主动引出 CAP、故障域隔离话题。
